# MVP: запуск приложения и проекты исследования

## Назначение и состояние

Этот документ фиксирует проверяемый первый вертикальный срез PaperWeave. Это **черновой** контракт, основанный на пользовательском PDF и более позднем прямом выборе frontend-стека пользователем. Он не является утверждённым Spec и сам по себе не разрешает начинать реализацию.

Цель среза — надёжно запустить локальное приложение, проверить доступность API, создать исследовательский проект, показать список/карточку проекта и сохранить данные в PostgreSQL так, чтобы они переживали остановку и повторный запуск.

## Пользовательский сценарий

1. Пользователь запускает приложение локально.
2. В браузере открывается PaperWeave и показывает состояние backend.
3. Пользователь вводит название и необязательное описание проекта и создаёт его.
4. Интерфейс обновляет список и позволяет открыть карточку проекта.
5. После остановки и повторного запуска список содержит сохранённый проект.

Поток: Vue + TypeScript + PrimeVue 4 → HTTP → FastAPI → прикладной сценарий Projects → PostgreSQL. UI не подключается к базе напрямую.

## Контракты поведения

### Конфигурация и локальный запуск

- Приложение запускается как локальная Compose-система из `db`, одноразовой миграции, `api` и `ui`.
- Единая конфигурация приложения задаётся в `config.toml`; в Git хранится `config.example.toml`, локальный файл игнорируется. `.env` не является пользовательским источником конфигурации.
- CLI-обёртка читает и валидирует TOML, передаёт Compose только нужные переменные окружения и монтирует конфиг в контейнеры в режиме read-only. Сервисы не вводят второй независимый конфигурационный источник.
- Значения по умолчанию: API `127.0.0.1:18741`, UI `127.0.0.1:18742`; PostgreSQL доступен только в сети Compose на 5432. Контейнерные процессы слушают `0.0.0.0`, публикация host-портов привязана к `127.0.0.1`. Порты можно изменить конфигурацией.
- `make init` создаёт локальную конфигурацию только при отсутствии и не перезаписывает существующий файл. `config-check`, `up`, `down`, `restart`, `logs`, `ps`, `migrate`, `test`, `help` имеют документированную семантику. `down` сохраняет данные; удаления volume/data-команды в MVP нет. `up` проверяет конфиг, собирает образы, ждёт БД, выполняет миграции, затем запускает API и UI; повторный `up` безопасен.
- Неизвестная/невалидная конфигурация приводит к ненулевому завершению с понятной ошибкой. Проверяются типы, обязательные поля, диапазоны портов и положительные таймауты. Пароль/DSN не попадает в логи.
- Параметры API/UI: health timeout 2 s, request timeout 10 s, health poll interval 10 s. Изменения TOML применяются после перезапуска процессов.

### HTTP API (`/api/v1`)

| Метод и путь | Успех | Поведение |
|---|---|---|
| `GET /health/live` | `200` | Процесс API работает; проверка БД не выполняется. |
| `GET /health/ready` | `200` или `503` | `200`, когда БД доступна; иначе `503` с признаком недоступности БД. |
| `GET /projects` | `200` | Список проектов, новые сначала. |
| `POST /projects` | `201` | Создать проект; UUID и UTC `created_at` задаёт backend. |
| `GET /projects/{project_id}` | `200`, `404`, `422` | Получить проект по UUID; неверный UUID — `422`, отсутствующий проект — `404`. |

Тело создания: `name` после trim обязателен, длина 1–200 символов; `description` необязателен, максимум 5000 символов. Одинаковые названия допустимы. В MVP нет редактирования/удаления проектов и пагинации.

### Модель хранения

Одна прикладная таблица `projects`: `id UUID PRIMARY KEY`, `name VARCHAR(200) NOT NULL`, `description TEXT NULL`, `created_at TIMESTAMPTZ NOT NULL`; служебная таблица Alembic хранит версию схемы. Изменения схемы только через последовательные Alembic migrations.

### UI

- Главная страница показывает название приложения, состояние backend, форму проекта, список, кнопку обновления и переход к карточке.
- Карточка показывает название, описание, ID, `created_at` и возврат к списку.
- При открытии главной страницы UI запрашивает readiness и список. Проверка здоровья повторяется каждые 10 секунд, не перекрывается с самой собой и останавливается при уничтожении страницы.
- Создание выполняет `POST`, затем обновляет список; кнопка блокируется на время отправки. Ошибка сохраняет введённые значения. POST автоматически не повторяется. Ручное обновление повторно получает список. Ошибка API не завершает UI аварийно.
- Состояния здоровья отображаются различимо: проверка, доступен, не готов, нет соединения.
- UI реализован на Vue, TypeScript и PrimeVue 4. Используются готовые PrimeVue-компоненты согласно отдельному [дизайн-коду](../design-system.md).

## Критерии приёмки

- `AC-1`: `make init` создаёт пример локального конфига только если его ещё нет; `config-check` выявляет ошибочные значения без раскрытия секрета.
- `AC-2`: локальная Compose-система собирается и проходит миграцию до старта UI/API; ошибка миграции не отображается как готовность.
- `AC-3`: интерфейс доступен на настроенном UI-порту по умолчанию 18742, API — на 18741; API и UI используют конфигурационные порты, а не скрытый порт 8000.
- `AC-4`: пользователь может создать проект, увидеть его в списке, открыть карточку и получить корректные поля.
- `AC-5`: проект сохраняется после `down` и повторного `up`; `down` не удаляет данные.
- `AC-6`: при недоступной БД readiness возвращает 503, а liveness остаётся независимой от БД.
- `AC-7`: при недоступном API UI сообщает об отсутствии соединения и продолжает работать; ошибки создания не стирают введённые данные.
- `AC-8`: настройки портов меняются через TOML без редактирования исходников и Compose-файла.
- `AC-9`: `make test` использует выделенную тестовую БД/ресурсы или изолированные заменители и не читает/изменяет пользовательскую рабочую БД.

## Границы MVP

Не входят загрузка/разбор PDF, LLM, embeddings/pgvector, очередь и worker, редактор рукописи/Tiptap, библиотека источников/evidence, аутентификация, совместная работа, удалённая публикация и production-развёртывание. Tiptap остаётся возможной будущей частью frontend-архитектуры, но не MVP-поведением.

## Разрешение конфликтующего описания стека

В приложенном PDF предлагается NiceGUI. Более позднее прямое указание пользователя в этом чате задаёт Vue + PrimeVue 4 + TypeScript и направление потока Vue → FastAPI → Python-сервисы/хранилища. Поэтому данный черновой контракт принимает Vue-frontend; NiceGUI в MVP не используется. Это происхождение решения, не утверждение о принятом ADR. PrimeVue имеет приоритет для стандартных элементов оформления согласно дизайн-коду.

## Проверка

Критерии проверяются тестами конфигурации, контрактов API и сценариев Projects на изолированных ресурсах, проверкой миграции и локальным браузерным/HTTP-сценарием. Наличие документов или сборка frontend сами по себе не доказывают готовность MVP.
