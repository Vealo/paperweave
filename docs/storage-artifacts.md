# Хранение пользовательских файлов

## Границы ответственности

PostgreSQL — каталог и источник истины для владения и жизненного цикла файла. Строка `file_artifacts` хранит владельца, тип (`avatar`, `image`, `document`), доменную связь, backend, bucket, opaque object key, исходное имя, media type, размер, SHA-256, версию, lifecycle, идемпотентный ключ и состояние очистки. Публичные и внутренние URL в таблицу не записываются. Клиент получает только API URL, который проверяет сессию и владельца.

Байты хранит выбранный backend: локальное файловое хранилище или S3 API SeaweedFS. API не выдаёт S3 credentials браузеру. В конфигурации секреты доступны API; SeaweedFS получает отдельный JSON с правами доступа из локальной директории с правами `0600`. SeaweedFS не публикует host ports. Его данные хранятся в отдельном Docker volume.

## Lifecycle

`pending_upload` резервирует идентичность перед записью байтов; `active` означает, что PostgreSQL ссылается на проверенный объект; `pending_delete` — удаление ожидает выполнения или повторной попытки; `deleted` сохраняет tombstone; `failed` предназначен для постоянной ошибки после операционной диагностики. Просроченные незавершённые upload reservations и оставшиеся `pending_delete` повторно обрабатываются при следующем старте API. Повторный DELETE для принадлежащего пользователю объекта из `pending_delete` также повторяет физическую очистку; повтор после завершённого удаления остаётся безопасным.

Замена аватара проходит в порядке: резервирование записи → запись и проверка нового объекта → одна транзакция PostgreSQL переключает активный аватар и ставит старый в `pending_delete` → удаление старого объекта → перевод в `deleted`. При сбое до переключения прежний аватар остаётся активным. Ошибка удаления не возвращает объект в активное состояние: запись остаётся в БД для повторной очистки. API при следующем старте повторяет объекты из `pending_delete`.

Удаление документа сначала проверяет владельца проекта и отсутствие ссылок на извлечённые доказательства. PostgreSQL переводит объект в `pending_delete` и удаляет доменную строку, затем backend удаляет байты. Ошибка оставляет tombstone и диагностический тип ошибки.

POST загрузки требуют `Idempotency-Key` (1–119 символов). Повтор в пределах типа операции с тем же ключом и содержимым возвращает исходный объект или продолжает незавершённую запись; повторное использование ключа с другим содержимым даёт HTTP 409. Области ключей аватара, изображения и документа независимы.

## Миграция и смена backend

Миграция `20261020_0010` создаёт каталог и регистрирует существующие PDF под теми же ID, ключами, версиями и checksums; ссылки источников и доказательств сохраняются. Уже сохранённые аватары также регистрируются, но их прежняя схема не содержала checksum и размер, поэтому миграция обозначает эти значения нулевым legacy маркером; следующая успешная замена запишет проверенные значения.

Backend выбирается через `[storage].backend`. Каталог хранит backend для каждого объекта, поэтому API читает и очищает объекты по записи каталога даже после переключения конфигурации. Сами байты между backend не копируются автоматически; перенос данных требует отдельной операции миграции объектов, которая копирует, проверяет и только затем меняет backend/key в транзакции PostgreSQL.

SeaweedFS запускается из Compose с закреплённым образом `chrislusf/seaweedfs:4.48`, S3 API доступен контейнерам на `seaweedfs:8333`. Переключение в `[storage]` на `backend = "s3"` требует доступного SeaweedFS и настроенных учётных данных. `GET /api/v1/health/ready` проверяет выбранный backend и может создать настроенный bucket при первом обращении.

## Типы и проверки

- `avatar`: PNG/JPEG/WebP на входе, сервер декодирует и нормализует в PNG; предел 5 MiB и 20 мегапикселей.
- `document`: PDF с сигнатурой `%PDF-`; предел 25 MiB; владелец определяется через проект и источник.
- `image`: PNG/JPEG/WebP; предел 5 MiB и 20 мегапикселей; декодируется, проверяется и нормализуется в PNG до сохранения.

Профильный API предоставляет `POST /api/v1/auth/me/images`, `GET /api/v1/auth/me/images/{id}` и `DELETE /api/v1/auth/me/images/{id}`. Изображения проходят ту же серверную проверку и нормализацию, что и аватар; чтение и удаление доступны только владельцу.

Для каждого нового объекта проверяется размер и SHA-256 прочитанных из backend байтов. Ключи генерируются сервером и никогда не строятся из имени пользователя.
