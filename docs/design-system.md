# Правила оформления интерфейса PaperWeave

> Документ задаёт правила реализации интерфейса. Стек: Vue 3, TypeScript, PrimeVue 4 и Tiptap. Базовая тема приложения — PrimeVue Aura; конкретные значения оформления берутся из её дизайн-токенов.

## Тема и установка

- Подключать `@primeuix/themes/aura` как preset через `PrimeVue` в `frontend/src/main.ts`.
- Использовать светлую схему по умолчанию, CSS-переменные PrimeVue и штатные состояния компонентов. Цвета приложения не дублировать литералами.
- Общие шрифты, ширину рабочей области и фон страницы задавать в `frontend/src/styles/`. Экранные файлы отвечают за компоновку, а не создают параллельную систему компонентов.
- Для стандартных действий, ввода, сообщений, карточек и загрузки применять `Button`, `InputText`, `Textarea`, `Message`, `Card` и `Skeleton` соответственно. Перед добавлением самописного контрола проверять каталог PrimeVue 4.
- Для семантической палитры применять единый preset `frontend/src/theme/paperweavePreset.ts`, собранный через публичный `definePreset` из `@primeuix/themes`; не переопределять цвета библиотечных компонентов локальными литералами.
- Для навигации использовать Vue Router; переходы должны оставаться доступными по прямой ссылке и поддерживать возврат к списку.
- Не применять тему/пресет через самописные CSS-переопределения. Если компоненту нужна индивидуальная вариация, сначала использовать его props, slots или Pass Through API.

## Приоритет готовых компонентов

1. Сначала проверить, подходит ли компонент PrimeVue 4 и его штатные параметры, слоты, template parts и дизайн-токены.
2. Если нужна комбинация компонентов, собрать её из компонентов PrimeVue и небольшого количества проектных обёрток.
3. Новый визуальный компонент создавать только когда готовый компонент не обеспечивает нужную семантику, поведение, доступность или композицию. Причину и повторное использование фиксировать рядом с компонентом.
4. Не копировать и не переписывать компонент PrimeVue ради локального отличия во внешнем виде. Настраивать его через поддерживаемую тему, токены, слоты и ограниченные CSS-классы.

PrimeVue — исходный набор UI-компонентов, но не источник предметных правил. Компоненты отображают состояние и отправляют пользовательские действия; backend и прикладные сценарии сохраняют контроль над доступом, доказательствами и изменениями рукописи.

## Правила построения оформления

- Использовать токены темы PrimeVue для цветов, типографики, размеров, границ, теней и состояний. Не вводить локальные значения, если соответствующий токен уже выражает нужный смысл.
- Для семантической палитры применять единый preset `frontend/src/theme/paperweavePreset.ts`, собранный через публичный `definePreset` из `@primeuix/themes`; не переопределять цвета библиотечных компонентов локальными литералами.
- Предпочитать семантические токены (`primary`, `surface`, `text`, `border`, `focus`, `danger`, `success`) прямым цветовым значениям.
- Выстраивать экраны из готовых компонентов по их назначению: формы и валидация — формы PrimeVue; действия — Button и Menu; выбор и фильтрация — соответствующие Select, Table, Tree или List-компоненты; сообщения состояния — Toast, Message и Progress-компоненты.
- Держать стили рядом с компонентом-владельцем и ограничивать область селектора. Глобальные стили предназначены только для сброса, шрифтов, базовой темы и общих токенов.
- Не использовать `!important`, глубокие глобальные селекторы и переопределение внутренних классов PrimeVue как обычный механизм настройки. Если публичной точки настройки не хватает, сначала проверить поддержку slot/PT и темы.
- Проектные обёртки должны добавлять только повторно используемую компоновку или единое поведение; они не должны скрывать доступные возможности PrimeVue без причины.
- Отделять визуальные состояния загрузки, пустого результата, ошибки, блокировки, выбора и подтверждённого действия. Для AI-предложения отдельно показывать его статус и действие автора.

## Header и активные действия

- Общий header приложения состоит из бренда, области активных действий текущего экрана и блока учётной записи. Предметные действия не размещать рядом с заголовком экрана или внутри карточки, если они должны оставаться доступны на странице.
- Область действий реализуется повторно используемой обёрткой `AppHeaderActions` (`frontend/src/components/AppHeaderActions.vue`) и содержит не более трёх элементов. Состав действий задаётся владельцем сценария в `App.vue` на основе текущего маршрута.
- Ссылки оформлять через `RouterLink` с готовым `Button` PrimeVue 4 (`severity="secondary"`, `text`); команды — таким же `Button` с обработчиком и явным состоянием `disabled`, если действие недоступно. Не создавать самописные HTML-кнопки или собственный dropdown.
- Название действия должно быть коротким и предметным, например «К списку проектов». Не использовать только иконку без доступного текстового имени.
- На широком экране область действий располагается справа от бренда и до блока учётной записи. На узком экране переносится на отдельную строку header, не скрывая и не уменьшая цель нажатия. Стили компоновки ограничивать классами `.app-header__actions` и `.app-header__inner` в `frontend/src/styles/main.css`; внешний вид кнопок оставлять штатным для PrimeVue.
- Не смешивать навигацию текущего экрана с настройками учётной записи, выходом и административной навигацией; для них сохраняются отдельные элементы header.
- Блок пользователя показывается как одна компактная кнопка PrimeVue `Button`: круглый `Avatar` и полное имя пользователя в одну строку. Аватар и имя всегда остаются видимыми вместе; длинное имя сокращается многоточием, а сами элементы не сжимаются независимо. Нажатие открывает стандартный PrimeVue `Menu`; в нём email находится в заголовке, затем идут настройки, административный пункт (если доступен) и выход.
- Пункт «Настройки» открывает PrimeVue `Dialog` с тем же переиспользуемым компонентом идентичности (аватар, имя, email) и штатным `FileUpload`. Раздел системных настроек пока содержит короткую заглушку. Загрузка аватара принимает PNG, JPEG и WebP до 5 MiB; сервер проверяет сигнатуру файла, ограничивает размер и сохраняет изображение в локальное хранилище профиля.
- Форма владельца для добавления пользователя использует те же компоненты `ProfileIdentity` и `ProfileAvatarPicker`, чтобы показать выбранный аватар и имя до создания записи. Сначала создаётся учётная запись, затем загружается её аватар; ошибка второго шага явно сообщает, что пользователь уже создан и аватар можно добавить позднее в настройках профиля.

## Рабочая зона проекта и модальные инструменты

- Главная рабочая область проекта — редактор рукописи. На странице редактора он занимает всю доступную ширину основного контейнера; навигация, сведения о проекте, библиотека источников и аргументация не образуют постоянные боковые колонки.
- Дополнительные инструменты вызываются кнопкой `Menu` PrimeVue рядом с заголовком «Рукопись». Каждый пункт открывает соответствующий полноразмерный `Dialog` PrimeVue с `modal`; все пункты меню используют одинаковый полноэкранный слой.
- Навигация по рукописи и контекст проекта показываются в отдельных диалогах. Библиотека источников и утверждения с evidence также открываются в отдельных диалогах; их компоненты монтируются при первом открытии и сохраняют состояние при последующих закрытиях.
- Переход из диалога навигации к разделу закрывает диалог, затем перемещает фокус редактора к выбранному заголовку. Переход из карточки утверждения работает так же.
- Список проектов использует целую карточку `Card` как одну ссылку `RouterLink`. Внутри неё не размещать другие интерактивные элементы: у карточки единая клавиатурная цель, заметное состояние `hover/focus-visible` и короткая подпись действия.
- Эти правила описывают компоновку. Внешний вид диалогов, карточек, кнопок, сообщений и меню остаётся на стороне штатных PrimeVue 4 компонентов и токенов темы.

## Полноразмерные модальные окна

- Любой блокирующий модальный сценарий занимает весь viewport: ширина `100vw`, высота `100dvh`, без внешних полей и скруглённой рамки. Модальное окно воспринимается как отдельный полноэкранный рабочий слой, как в интерфейсе edx.ru.
- Компактные временные действия оформляются `Menu`, `Popover` или `Tooltip`, а не уменьшенным модальным окном. Подтверждение, форма, настройки и рабочие панели, перекрывающие страницу, используют полноэкранный режим.
- Во фронтенде применяется PrimeVue 4 `Dialog` с `modal` и общей утилитарной меткой `.pw-modal-fullscreen`; единые геометрия, безопасные поля и прокрутка заданы один раз в `frontend/src/styles/main.css`. Общая настройка PrimeVue Pass Through растягивает mask и убирает его внутренние поля: PrimeVue задаёт выравнивание mask встроенным inline-стилем, поэтому одного CSS-класса для этого недостаточно. Не переопределять размеры отдельного диалога без отдельного требования.
- Заголовок с названием сценария и штатная кнопка закрытия остаются видимыми сверху; содержимое прокручивается внутри окна, а нижние действия остаются видимыми в закреплённой области `footer`. Учитывать safe area мобильных устройств.
- Сохранять штатные PrimeVue управление фокусом, закрытие по Escape и доступное имя окна. На мобильном viewport полноэкранное поведение остаётся тем же, без перехода обратно к карточному диалогу.
- Класс `.pw-modal-fullscreen` обязателен для каждого PrimeVue `Dialog` проекта, включая диалоги настроек, создания проекта, навигации, контекста, библиотеки и утверждений.

## Цветовая система и активная тема

- Единственная активная тема интерфейса — светлая. Настройка ОС или профиля не должна включать тёмное оформление. Тёмная тема целиком отложена до отдельной задачи с собственным набором токенов и проверкой контрастности всех компонентов.
- Палитра ниже применяется как система небольших акцентов на нейтральных поверхностях. Не заливать её цветами фон страницы, карточек, рабочих панелей и модальных окон.
- Основное действие использует `#5B7917` с белым текстом. Тёмный вариант этого же акцента — `#0D3500`, для `hover` и `active`; это оттенок состояния элемента управления, а не включение тёмной темы.
- `#305700` — цвет ссылок и выразительных акцентов на светлой поверхности. `#899D31` — небольшие маркеры, выбранное состояние и неблокирующие индикаторы. `#B9C24B` — только мягкая подсветка или декоративный маркер; не использовать его для текста и тонких границ на белом.
- Белый текст допустим на `#5B7917` и `#0D3500`; на `#899D31` и `#B9C24B` текст должен быть тёмным. Статус или согласие не передавать только цветом: рядом сохранять текст, иконку или иной понятный признак.
- Цвета задаются централизованно через семантические токены PrimeVue/Aura и общие токены PaperWeave в `frontend/src/styles/`. Компоненты используют роли `primary`, `primary-hover`, `link`, `focus`, `selected` и `surface`, а не собственные литералы. Светлые поверхности, основной текст и приглушённый текст остаются нейтральными; фон и цвет текста каждого компонента должны происходить из одной активной схемы.
- Единственный владелец цветовых значений — набор `--pw-*` токенов в начале `frontend/src/styles/main.css`; `frontend/src/theme/paperweavePreset.ts` связывает их с публичными semantic tokens PrimeVue/Aura (`primary`, `focusRing`, `highlight`). Стили приложения используют те же роли (`--pw-color-link`, `--pw-color-focus`, `--pw-surface-selected`), не копируя HEX.
- Семантические сообщения используют тёмные цвета текста на светлых поверхностях: `--pw-color-info` (`#1d4ed8`), `--pw-color-success` (`#166534`), `--pw-color-warning` (`#854d0e`) и `--pw-color-danger` (`#b91c1c`). `paperweavePreset.ts` назначает их базовому, outlined и simple вариантам; цвет дополняет текстовую метку/иконку и не является единственным носителем статуса.
- Контраст палитры с белым фоном: `#5B7917` — 5.01:1, `#305700` — 8.44:1, `#0D3500` — 13.76:1, `#899D31` — 3.03:1, `#B9C24B` — 1.93:1. Поэтому обычный текст и подписи действий используют первые два основных оттенка; последние два остаются ограниченными небольшими графическими акцентами и мягкой подсветкой.

| Роль | Токен | Цвет / пара | Применение |
|---|---|---|---|
| Основное действие | `--pw-color-primary` / `primary.color` | `#5B7917`, белый текст `5.01:1` | Кнопки и главный брендовый маркер |
| Наведение и активное действие | `--pw-color-primary-strong` / `primary.hoverColor`, `primary.activeColor` | `#0D3500`, белый текст `13.76:1` | Hover/active кнопок и текст выбора |
| Ссылка | `--pw-color-link` | `#305700`, белый фон `8.44:1` | Текстовые ссылки и навигационные акценты |
| Фокус | `--pw-color-focus` / `focusRing.color`, `formField.focusRing.color` | `#899D31`, белый фон `3.03:1` | Обводка клавиатурного фокуса толщиной 2 px |
| Маркер | `--pw-color-marker` | `#899D31` | Небольшая графическая метка; не обычный текст |
| Мягкий акцент | `--pw-color-subtle` | `#B9C24B`, белый фон `1.93:1` | Декоративная подсветка с тёмным текстом; не текст/граница на белом |
| Выбранная поверхность | `--pw-surface-selected`, `--pw-surface-selected-hover` | `#f4f7ed`, `#e8eed8`; `#0D3500` поверх — `12.69:1` / `11.57:1` | Мягкая нейтральная заливка выбранного состояния |

## Доступность и адаптация

- Сохранять нативную семантику и доступное имя интерактивных элементов; клавиатурная навигация и видимый focus обязательны.
- Не передавать значение только цветом: статусы сопровождать текстом или доступной подписью.
- Для цветных сообщений использовать тёмные foreground-токены из `paperweavePreset.ts` на светлом компонентном фоне; для текстовых действий ошибки использовать тёмный семантический оттенок (`--p-red-700` или контрастнее). Статусы успеха, предупреждения и ошибки всегда содержат текстовую метку или доступное имя, поэтому их смысл не зависит только от оттенка.
- Формы показывают связанную с полем ошибку и не теряют введённые данные при её появлении.
- Проектировать сначала для рабочего экрана исследователя; при сужении окна сохранять ключевые действия и контекст источника, адаптируя компоновку, а не просто уменьшая элементы.
- Состояние интерфейса должно оставаться понятным при долгих операциях и ошибках внешних провайдеров.

## Редактор рукописи

Tiptap отвечает за редактирование и представление содержимого документа. Его меню и панели по возможности строятся из PrimeVue. Стилизация области редактора должна визуально отделять авторский текст, цитаты и пометки происхождения, не создавая видимость, что Tiptap сам проверяет доказательства.

До реализации нужно определить модель документа, поддерживаемые узлы/marks, сохранение версий, поведение вставки из источников и отображение ссылок на доказательства. Эти решения нельзя прятать в CSS или компонентах редактора.

## Границы файлов оформления

- `frontend/src/styles/` — общие импорты темы и только проектные токены/глобальные стили.
- `frontend/src/components/` — проектные повторно используемые обёртки над PrimeVue, когда они оправданы.
- `frontend/src/editor/` — Tiptap-конфигурация и стили редактора; общие правила темы сюда не дублировать.
- `frontend/src/views/` — композиция экранов; локальные стили здесь допустимы только для компоновки конкретного экрана.

При появлении повторяющегося UI сначала сверять его с компонентами PrimeVue и этими правилами. Новый паттерн оформления документировать здесь только если он нужен нескольким экранам или задаёт системное поведение.
