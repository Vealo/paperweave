# Анализ IMP-2026-002 — доменное развитие PaperWeave

**Дата:** 2026-10-19
**Baseline:** `1aedd023eb89fce799ea75e345cf9035f9aa48a1`
**Источники:** пользовательский запрос «Оформи следующим этапом: расширяем документацию планы реализации (по доменам)» и приложенная концепция исследовательского рабочего пространства от 2026-10-19.
**Область:** только плановые документы; реализация функций и регистрация Tasks в этот запрос не входят.

## Запрос и целевой результат

Сохранить концепцию рабочего пространства как карту доменов и оформить последовательный план дальнейшего развития после узкой локальной основы MVP. Автор остаётся владельцем рукописи и решений по evidence; интерфейс показывает контекст, но доменные данные принадлежат backend-сценариям. План охватывает доступ, рабочее пространство, рукопись, источники, извлечение документов, evidence, AI-предложения и экспорт как отдельные доменные срезы.

Исключены из текущей документационной задачи: код, миграции, запуск сервисов, регистрация implementation Tasks, выбор внешних провайдеров, push, CI и deployment.

## Текущая архитектура и повторное использование

Vue 3 + TypeScript + PrimeVue 4 уже обслуживают проекты; FastAPI вызывает Python application services, а PostgreSQL хранит проекты. Целевая архитектура описывает отдельные модули `projects`, `manuscripts`, `library`, `evidence`, `jobs`, adapters `documents`, `llm` и `scholarly`, но они ещё не реализованы. Tiptap — редакторская интеграция, не владелец бизнес-состояния. Файлы обслуживаются через storage boundary; внешние действия AI/поиска должны проходить через явный adapter.

| Граница | Владелец | Переиспользуемое | Ограничение |
|---|---|---|---|
| HTTP API | FastAPI endpoints | текущий router/dependency pattern | Endpoint не должен владеть persistence или правилами предметной области |
| Application | Python services | `ProjectService` pattern | API и worker должны вызывать общие сценарии, если worker будет обоснован |
| Persistence | SQLAlchemy/Alembic/PostgreSQL | текущая инфраструктура БД | Требуется миграционная совместимость; детали доменных схем открыты |
| Frontend | Vue/TypeScript/PrimeVue 4 | готовые PrimeVue-компоненты и API client | Tiptap отвечает за редактирование/представление, не за каноническое сохранение |
| File/LLM/scholarly adapters | integrations/storage | только целевые boundaries | Провайдеры, форматы и privacy controls пока не утверждены |

## Архитектурная проверка

**Вердикт:** `needs_decision`, ограниченный P1; остальные фазы не получают разрешения на реализацию этим документом и остаются зависимыми от контрактов/предыдущих фаз.

**ACF-1 — blocking, scope: phase, phase: P1.** Кодовая база не определяет владельца пользовательской идентичности, способ создания аккаунта, модель сессии, границу удалённого deployment и правила присвоения текущих проектов пользователям. Это влияет на приватность и запрет межпользовательского доступа. **Владелец решения:** Denis Karmalak (владелец проекта, указан в ADR-0006). **Условие снятия:** утвердить продуктовый контракт входа, provisioning и сессии; определить целевой режим использования и безопасную миграцию существующих проектов. **Следующий шаг:** принять/уточнить решение и записать его в Spec/ADR до начала P1 implementation Task.

**ACF-2 — informational, scope: phases P2–P8.** ADR-0002…0005 и модели данных остаются предложениями, поэтому каждая доменная фаза сначала фиксирует свой поведенческий/data contract и необходимое решение; не выводить принятие из этого плана. **Владелец:** владелец проекта. **Условие:** контракт конкретной фазы согласован до её реализации. **Следующий шаг:** уточнять фазу только при приближении к её запуску.

Проверка не принимает новые ADR и не утверждает решения за владельца.

## Общие ограничения и безопасный порядок

- Сохранять текущий MVP для локальной разработки; не менять его контракт молча.
- Не вводить отдельную сущность для UI-компонента, если она не имеет самостоятельной идентичности, жизненного цикла и инвариантов.
- Не считать наличие цитаты доказательством поддержки Claim; extraction и AI-результаты не являются проверенными без решения автора.
- Не отправлять пользовательский контент AI-провайдеру без явного контекста, политики передачи и наблюдаемой ошибки.
- Не добавлять регистрацию, совместную работу, приглашения, production deployment и внешние provider APIs автоматически.
- Каждая схема/миграция должна сохранять обратимую и проверяемую стратегию для локальных данных; пользовательские/production данные не входят в текущую авторизацию.
- Никаких внешних эффектов, production изменений и разрушительных миграций в этой документационной работе.

## Предлагаемая последовательность

| Фаза | Домен | Результат/гейт |
|---|---|---|
| P1 | Identity and access | Утверждён пользовательский контракт доступа и безопасная привязка проектных данных |
| P2 | Manuscripts | Сохранение одной рукописи с упорядоченными блоками и восстановлением после ошибок сохранения |
| P3 | Project workspace | Главный экран проекта, навигация по проекту/документу и раздельные статусы сохранения/API/AI |
| P4 | Library | Метаданные источников и контролируемое хранение пользовательских файлов |
| P5 | Documents | Извлечённые фрагменты, страницы/anchors и состояния повторной обработки без ложного статуса evidence |
| P6 | Evidence | Claim и типизированные связи с SourcePassage, человеческая проверка и прослеживаемость к блокам рукописи |
| P7 | AI assistance | Контекстное предложение с preview/accept/reject, сохранением оригинала и ограничением передачи данных |
| P8 | Citations and export | Выбранное представление цитат и экспорт с проверкой ссылок на источники |

Последовательность — зависимостная, а не календарная. Каждая фаза получает собственный уточнённый контракт и task package только при явном запуске; точные acceptance criteria нельзя выводить из этой концепции без доменного уточнения.

| Как пользователь получает учётную запись: локальная подготовка владельцем, открытая регистрация или приглашение? | Определяет поверхность abuse и жизненный цикл аккаунта | Denis Karmalak | Не реализовывать UI/API входа и не объявлять проекты приватными до решения |

## Вердикт анализа

`ready_with_blockers`: документационную карту и последовательность доменных срезов можно зафиксировать. Реализация P1 заблокирована решением ACF-1. P2–P8 являются зависимыми будущими срезами; их описание не является утверждённым behavior contract или разрешением на выполнение.
