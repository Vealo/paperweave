# ADR-0002: Модульный монолит и начальный технический стек

## Контекст и проблема

Первой версии нужен цельный путь от библиотеки PDF до рукописи со ссылками на доказательства — без преждевременного разделения на распределённые сервисы и без обязательства сразу создавать сложный rich-text editor и платформу агентов.

## Требования и ограничения

- Сохранить первую реализацию развёртываемой и понятной как единая система.
- Разделить ответственность предметных областей и код внешних интеграций.
- Предусмотреть worker для долгих операций импорта, извлечения данных и вызовов моделей.
- Не привязывать границы приложения к одному поставщику моделей или хранения.
- Исходный набор вариантов предложен пользователем; последующие прямые выборы и реализация MVP имеют более узкую область. Этот ADR остаётся предложенным целиком и не превращает невыбранные компоненты в принятые решения.

## Рассмотренные варианты

| Вариант | Преимущества | Издержки и риски |
|---|---|---|
| Python modular monolith | Небольшая поверхность развёртывания, ясные внутренние границы, постепенная реализация vertical slice | Требует дисциплины в разделении модулей и направлении зависимостей |
| Сразу распределить систему на сервисы | Независимое масштабирование и развёртывание подсистем | Добавляет сетевые контракты, операции и отказы до понимания нагрузки |
| Сразу взять отдельный browser editor и backend | Больше контроля над редактором | Усложняет frontend до проверки исследовательского сценария |

## Предлагаемое решение

Начать с Python modular monolith для backend и отдельного frontend-приложения на Vue 3, TypeScript и PrimeVue 4. Для редактирования рукописей использовать Tiptap как редактор на Vue; его schema/extensions и сериализацию определить отдельно. Предлагаемые backend-компоненты: FastAPI + Pydantic для HTTP, PostgreSQL + pgvector через SQLAlchemy + psycopg, migrations на Alembic, LiteLLM SDK за внутренним `LLMService`, локальное файловое хранилище за storage-интерфейсом, отдельный Python worker, Docker Compose и pytest.

Предлагаемая структура разделяет `frontend/` (Vue, PrimeVue, Tiptap, TypeScript) и `src/paperweave/` (API, прикладные services, доменные modules, integrations, infrastructure и `worker.py`). Frontend и worker используют одну и ту же границу прикладных сценариев на backend. В `pyproject.toml` записаны предварительные диапазоны Python-зависимостей; build backend, поддерживаемая версия Python, sync/async-режим БД и очередь не выбраны.

## Область действия

Начальная структура кода и deployment, а также ответственность модулей. Решение не выбирает production-платформу, queue broker, провайдера научных источников или authentication.

## Последствия и компромиссы

Backend может стартовать как единая кодовая база, а worker — как дополнительный процесс/container; frontend собирается отдельным приложением и общается с backend по HTTP API. PostgreSQL и pgvector позволяют сначала не вводить отдельную vector database, но сам сценарий векторного поиска ещё нужно подтвердить. Vue/PrimeVue/Tiptap дают специализированную browser UI и редактор; это увеличивает начальную стоимость frontend-сборки и требует явного API-контракта.

## Переход и совместимость

Сохранять доменные контракты независимыми от Vue-компонентов, PrimeVue и Tiptap, LiteLLM SDK, SQLAlchemy sessions и путей файловой системы. Backend API — единственная граница связи frontend с предметными сценариями. Не разделять backend на сервисы, пока независимое масштабирование, надёжность или владение не оправдают дополнительные издержки.

## Риски и основания

Локальная узкая основа MVP реализована и проверена по [IMP-2026-001](../plans/imp/imp-2026-001-mvp-foundation.md): TOML/Compose, FastAPI, PostgreSQL/Alembic и Vue/PrimeVue UI проектов. Этот факт не принимает ADR целиком: Tiptap, pgvector, LLMService, файловое хранилище, worker, production deployment и другие будущие компоненты остаются предложениями; точные версии зависимостей закреплены lock-файлами.

## Принятие решения

Не принято. Владелец решения и явное принятие не зафиксированы.
